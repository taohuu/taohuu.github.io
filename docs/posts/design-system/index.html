设计系统从零到一：我的踩坑与收获

John Doe 2026年5月20日

为团队构建设计系统是一次充满挑战的旅程。从最初的概念验证到最终全团队采用，整个过程历时半年。这篇文章记录了我的踩坑经历和最终收获。

为什么需要设计系统？

当时团队面临几个痛点：

  1. 视觉不一致：同一个按钮在不同页面有 6 种样式
  2. 沟通成本高：设计师和开发者对"16px 的间距"有不同理解
  3. 重复造轮子：每个新项目都在重新写基础组件

第一步：设计令牌（Design Tokens）

设计令牌是整个系统的基石。我们把所有设计决策编码为可复用的变量。

:root {
  --color-primary: #4a90d9;
  --color-text: #1a1a1a;
  --space-sm: 8px;
  --space-md: 16px;
  --space-lg: 24px;
  --radius-sm: 6px;
  --radius-md: 12px;
  --font-size-body: 1rem;
}

关键原则：语义化命名 > 值命名。用 --color-text 而不是 --color-gray-900，这样换主题时只需改值。

第二步：组件库

从"最小可行组件集"开始，而不是试图覆盖所有场景：

  • Button（按钮）
  • Input（输入框）
  • Card（卡片）
  • Typography（排版）
  • Icon（图标）

我们选择了 组件驱动开发 的方式——每个组件都在隔离环境中开发和测试。

最大的三个坑

坑一：过早抽象

一开始我试图设计一个"完美"的 Button 组件，支持 47 种变体。结果代码复杂、难以维护。

教训：先具体，后抽象。 出现第三次重复代码时再考虑抽象。

坑二：忽略可访问性

最初的组件颜色对比度不足，键盘导航也有问题。后来我们引入了自动化 a11y 测试。

坑三：文档没人看

花了两周写文档，结果没人读。后来改为活文档——每个组件旁边都有可交互的示例，这才是有效的文档。

收获

6 个月后，团队的交付速度提升了约 40%，视觉一致性显著改善。但最大的收获是：设计系统不只是组件和代码，它是设计师和开发者之间的共同语言。
