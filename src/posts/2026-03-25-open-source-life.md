两年前我发布了一个开源项目——一个 React 表单库。本来只是为了解决自己的需求，没想到慢慢积累了一千多个 GitHub stars 和一个活跃的社区。

维护开源项目的经历给了我很多意料之外的收获，也让我对"开源精神"有了更真实的理解。

## 日常是什么样的？

一个有活跃用户的开源项目的日常大概是这样：

- **早上**：打开 GitHub，看看昨晚有没有新 issue。通常有 2-3 个
- **白天**：正常工作（开源不是我的全职工作）
- **晚上**：花 1-2 小时处理 issue、review PR、回复讨论
- **周末**：花半天到一天写代码、更新文档

> 开源维护者不是在写代码，就是在讨论代码的路上。

## 最让我头疼的四种情况

### 1. "为什么不支持 X？"

有些 issue 是纯粹的需求索取，没有讨论，没有 PR——像是理所当然的功能请求。

我的处理方式：礼貌地解释项目范围和优先级，邀请对方提交 PR。**大多数人不回复，但偶尔有人真的提交了——这就是开源的魅力。**

### 2. 过时的 issue

"这个 bug 修复了吗？"——发布于 18 个月前，已经在 v2.0 修复了。

解决办法：自动化的 issue bot 给过期 issue 打标签。

### 3. 文档不够好

这是最合理的批评。写文档是枯燥的工作，但**好的文档比好代码更能留住用户**。

我后来把文档贡献也计入 Contributors 页面——这极大地改善了文档质量。

### 4. 倦怠

连续处理三周 issue 后开始感到疲惫。开源维护的倦怠是真实的，而且很少被讨论。

## 社区运营的几点心得

### 贡献者阶梯

- **Level 1**：提 issue 的用户
- **Level 2**：回复 issue 的活跃用户
- **Level 3**：提交小修复的贡献者
- **Level 4**：提交大功能的贡献者
- **Level 5**：获得 triage 权限的维护者

给每个层级清晰的晋升路径，让贡献者看到成长空间。

### 善用模板

Issue 模板和 PR 模板可以节省大量重复沟通。我的 Bug Report 模板要求：

1. 重现步骤
2. 期望行为 vs 实际行为
3. 环境信息（版本、浏览器等）
4. 最小重现代码

**缺一条不完整的信息，我就礼貌地指回模板。**

### 说"不"的能力

这是最难的。不是每个 PR 都要合并，不是每个功能都要支持。说"不"不是不友善，而是保护项目的质量边界。

## 开源给了我什么？

1. **代码质量意识**：知道别人会看你的代码，写得更认真
2. **英语能力**：和全球开发者交流，英文读写大幅进步
3. **设计决策能力**：每一个 API 接口都要经过多方讨论
4. **职业机会**：因为这个项目，我收到了几个很好的工作邀请

最大的收获是：**学会了在公开场合理性讨论技术问题**——这种能力在日常工作中同样有用。

## 如果你想开始

1. 解决你自己的一个真实问题（而非凭空创造）
2. 写好 README——前 30 秒决定用户是否留下
3. 保持库小——一个库做好一件事
4. 不要追求 stars——关注真正在使用的人

> 开源不是免费的劳动，而是一个用代码连接同道中人的方式。
